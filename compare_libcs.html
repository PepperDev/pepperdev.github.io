Notes

In general

For each comparison in the table, each library is marked in red, yellow, or green. Red or yellow indicates that the library fails to support a feature or satisfy an optimality condition that may be desirable to some users.

Values marked with ? have not yet been tested. Contributions welcome!

Performance and bloat metrics are measured automatically via the libc-bench and libc-features tools. Feature rows with ? require manual verification or cross-compilation testing.

  • musl 1.1.5 (built from source)
  • glibc 2.19 (cross-compiled from source)
  • uClibc 0.9.33.2 (built from source)
  • uClibc-ng - not yet tested
  • dietlibc 0.32 (built from source)

Bloat comparison (storage)

"Bloat" refers to overhead cost that does not contribute to the functioning of an application. Sizes are measured via size(1) on the static/shared library sets and on the smallest programs. The "Smallest static C program" is int main() {}; "Static hello" is printf("hello %d\n", argc). Both are built statically with -Os and stripped, and their size row reports the size(1) text+data+bss total (raw file size would include ELF headers and alignment padding); the stripped file size is shown in the tooltip as fsize. dietlibc is linked the way its diet wrapper intends (-nostdlib plus its own start.o). uClibc here is built leaner than the original comparison, which used a locale-enabled Buildroot configuration.

Bloat comparison (memory)

Overhead is measured in dirty pages (Private_Dirty from /proc/$pid/smaps) for a program spinning in an infinite loop. Each probe spins on a fixed iteration count with no libc calls (the original int main() {} and printf hello), so the measurement reflects the libc's own footprint, not the probe's. The overhead binaries are built at the default -O2, unstripped; optimization level and stripping only change code size (clean pages) and non-alloc sections, so they do not affect dirty pages. Because dirty pages are quantized to 4k and one run carries ±1 page of ASLR noise, the reported value is the minimum over several runs.

Behavior on resource exhaustion

These compare robustness of interfaces under low resource conditions. Reporting failure is the theoretically optimal behavior (green). Each probe runs in a forked child of a dynamically-linked binary under memory exhaustion (RLIMIT_DATA 128 MB, malloc arena drained, address space filled with mmap); an abort or crash is recorded, not fatal. Divergences from the original comparison (measured vs 2009-era values, all version differences, not methodology): TLS — measured "reports failure" everywhere, original said glibc/uclibc abort and dietlibc n/a (dietlibc's loader has no TLS support at all: dlopen of a TLS module crashes even without exhaustion); pthread_cancel — uclibc "no failure" here (LINUXTHREADS_OLD has no libgcc_s cancel path), dietlibc "no failure" (orig n/a); regcomp — uclibc/glibc "reports failure" here vs "crashes" in 2009; fnmatch — uclibc "no failure" (orig unknown), glibc "reports failure" (orig) not reproduced in 2.19; printf — glibc "no failure" (orig "reports failure"; 2.19 has no such path, its wide-buffer malloc only aborts on %.100000f); strtol unchanged ("no failure" everywhere).

Performance comparison

All performance figures are from the libc-bench suite. Times are in seconds by default (no unit suffix). Values under 1ms are shown in milliseconds (ms), values under 1µs are shown in microseconds (µs).

The three allocation-contention rows (local, shared, ncpu threads) measure how each allocator scales under multithreaded allocation. The ncpu threads row (malloc_thread_ramp) sweeps the thread count up to the number of CPUs and reports wall time; it exists to test the claim that musl's default allocator collapses under futex contention as threads ramp up. See the references below.

UTF-8 decode rows show timeout for libcs whose locale does not report UTF-8 (uclibc, dietlibc in this build). The benchmark bails out before any decoding occurs; the recorded value is exit 124, not a real decode time.

Features comparison

Feature rows are detected programmatically: runtime probes (libc-features, inside the empty-rootfs container) overlaid on host-side nm/file/filesystem analysis (features_sys() in build.sh). The original comparison lists columns in the order musl / uClibc / dietlibc / glibc; this report orders them musl / glibc / uClibc / dietlibc. Divergences from the original comparison are honest measurements of the versions we build, not methodology:

  • C99 math library — symbol presence for 25 C99 functions (expm1, erf, j0, hypot, fma, …) counted across libm.a/libc.a. musl is complete; glibc 2.19 lacks fma and dietlibc lacks seven (cbrt, tgamma, nextafter, fmax, fmin, remquo, scalbn), both "partial"; uclibc 0.9.33.2 ships only expm1/copysign/scalbn, honestly "no" though the original said "partial".
  • Conformant printf — a 19-case score (width/flags, %e, %g, hex float %a, positional, %zu, %Lf, %*d). musl and glibc pass all; uclibc lacks %a (partial, the original said "no"); dietlibc 0.32 fails %e/%a/positional/%Lf, honestly "no" though the original said "yes".
  • Thread priority — a real SCHED_FIFO thread with PTHREAD_EXPLICIT_SCHED. musl/glibc/uClibc fail create with EPERM unprivileged (an honest attempt, so "yes"); dietlibc's attr setters return ENOTSUP/EINVAL, so "no".
  • Wide character interfaces — presence of the core wide API (wcstombs, swprintf, fwide, wcstod, …). dietlibc carries only five of eleven and lacks wcstombs and swprintf, so "minimal" (the original agreed).
  • C11 threads — detected by linking thrd_create against the header's declaration; only musl ships <threads.h>.
  • C11 thread-local storage — a forked child accesses a _Thread_local variable; uclibc and dietlibc segfault (no working TLS in these configs), musl and glibc pass. The original said uclibc "yes".
  • POSIX process scheduling — musl's sched_getscheduler stubs ENOSYS; glibc/uClibc/dietlibc report SCHED_OTHER and EPERM on real-time priority (kernel-correct). The original called glibc/uClibc "incorrect" and dietlibc "no".
  • Zoneinfo — a binary TZif file with a +1h offset is written and read via TZ=:/path; musl and glibc honor it, uclibc and dietlibc ignore it (dietlibc ignores even POSIX TZ strings). The original said dietlibc "yes".
  • TCB shadow — the container bakes /etc/tcb/itestuser/shadow; only musl's getspnam reads it.
  • Iconv — a probe counting iconv_open across nine UTF-8 pairs (decode and encode; musl converts all six decodes but cannot encode to CJK, dietlibc opens only ISO-8859-1/UTF-16). glibc runs dynamically through the sysroot loader with GCONV_PATH (static binaries cannot dlopen gconv) and opens all nine. The original said uclibc "mainly UTFs" and dietlibc "no".
  • Sun RPC — checked against the shared libc.so.6 dynamic symbols (glibc exports clnt_create); uclibc was built with __UCLIBC_HAS_RPC__ undefined and dietlibc has no RPC, both honestly "no" though the original said "yes".
  • Legacy 8-bit codepages / CJK — require setlocale data; a locale-archive (en_US.UTF-8, de_DE.ISO-8859-1, ja_JP.EUC-JP, zh_CN.GB2312) is generated into the glibc container via its own localedef. uclibc has no locale support (__UCLIBC_HAS_LOCALE__ undefined), so those rows are "no".
  • GCC libstdc++ compatibility — libstdc++-v3 is built per libc in a separate best-effort tree (gcc-final itself keeps --disable-libstdc++-v3 so a libstdc++ failure never breaks the compiler). The row is a C++ probe compiled with the target g++, linked statically, and run inside the container: it throws an exception, uses iostream, and grows a vector. A libc where libstdc++ fails to build is "no"; one where it links but the probe crashes at runtime (uclibc 0.9.33.2 unwinding) is "broken". Both render red.
  • Gmon profiling — dietlibc carries no monstartup/ _moncontrol symbols, so its row is honestly "no" though the original said "yes".
  • Target architectures — unlike the original, cells are measured, not taken from each project's documented port list. A cell is "yes" only when the libc cross-compiles for that architecture with our toolchain AND a hello program statically links against it (verifies crt objects, headers, libm, and the linker script — failures the libc build alone cannot catch). For every target with a qemu-user package the hello is then run under the emulator (host-runnable targets included, so the result does not depend on the host architecture); a link that will not run records "broken". "fail" means the libc builds but a user program will not link; "no" means the libc itself fails to cross-compile; "?" means untested (no toolchain for that architecture, or the libc declares no upstream port so testing is meaningless). Targets with no qemu-user package (x32, 31-bit s390) skip the run and count as "yes". Mainstream architectures (i386, ARM, AArch64, MIPS, PowerPC, RISC-V) come first; exotic ones only where the libc claims a port; AVR ATtiny, ESP32, and PIC 8-bit apply to newlib/picolibc only. The original marks musl aarch64, S/390x, and m68k "yes", but those ports landed in musl 1.1.7, 1.1.16, and 1.1.18 respectively — after the pinned 1.1.5 — so here they are "no" with the reason on the cell. Each was verified by running the real build: musl 1.1.5's configure rejects these targets ("unknown or unsupported target"). The same run recorded musl's other unlisted targets (sparc, alpha, 32-bit s390, riscv) as "no". Results accumulate in results/<libc>_arch.csv, one line per architecture.

License

The choice of license affects the usability of a standard library implementation. GPL v2-only is the most restrictive, incompatible with GPL v3-only code. MIT or BSD are the most flexible.

Maintainability

Main contributors are counted as unique authors with at least 10% of current LOC (via git blame on the default branch, run by build.sh into results/<libc>_contrib.csv). Counts not yet generated fall back to hard-coded values. Last release dates (newest release per libc, not the tested version) are fetched from each project's release page by build.sh; color reflects age (up to 6 months green, up to 2 years yellow, older red). Bootstrap issues describe the challenges of building each libc without an existing C library.
